# Alumni サイト情報設計 / Blueprint

## 1. 目的

Alumniサイトのコンテンツを「誰に向けた情報か」「サイト上でどの階層に属するか」「どのようにメニューや公開画面へ現れるか」という観点で整理する。

この文書は、Alumni Coreを利用して構築するサイト全体の情報設計と、現在確定している標準サイト構成のBlueprintとする。

## 2. 基本原則

Alumni Coreはコンテンツそのものと、その公開上の構造を管理する。

Themeは同じデータを利用して、レイアウトとナビゲーションの見せ方を変更する。

```text
Alumni Core
  ├── コンテンツ / 専用機能
  ├── 対象者カテゴリ
  ├── コンテンツ階層
  ├── Menu Structure
  ├── Homepage Grid
  └── 公開状態
          ↓
       Theme
          ↓
  Formal / Simple の表示
```

重要な原則は以下の3つを分離すること。

> 「何を表示するか」
> 「どこに属するか」
> 「どう見せるか」

## 3. 大カテゴリ

最上位の対象者カテゴリとして、以下を基本とする。

- 卒業生向け
- 在校生向け
- 共通

「在校生向け」は学校が発信する情報ではなく、**同窓会が在校生に向けて発信する情報**を意味する。

例：

```text
在校生向け
└── 卒業生の声
```

学校行事や学校公式のお知らせ等、学校側が主体となる情報はAlumni Coreの対象範囲に含めない。

## 4. Menu Structureとコンテンツ階層の分離

サイトナビゲーションの親子関係はMenu Structureを正本とする。

コンテンツそのものの親子関係と、メニュー上の親子関係は別物として扱う。

同じコンテンツを複数のメニュー位置から参照できる構造を維持する。

```text
Menu Structure
  共通
   └─ お知らせ

Content hierarchy
  （別の概念）
```

Theme側がコンテンツ階層から独自にメニューを再構築してはいけない。

Menu Structureでは以下を扱う。

- folder
- content
- system
- officer_list

フォルダはナビゲーション上の整理単位であり、コンテンツ種別ではない。

## 5. コンテンツ種別と管理画面の入口

「コンテンツ種別」を編集画面のラジオボタンで変更する方式は採用しない。

管理者は最初に目的に応じた入口を選ぶ。

```text
自由コンテンツを追加
人物挨拶を追加
規約類を追加
組織図を管理
校歌・校訓を管理
役員・理事を管理
```

各機能は必要なデータ構造を持つ。

編集画面に「自由コンテンツ / 人物挨拶 / 規約類 / フォルダ」等のラジオボタンを設けない。

特にフォルダはコンテンツではなく、Menu Structure側で作成する。

既存データ互換性のために内部的なkind等を保持することは妨げないが、新UIで種別変更を促す必要はない。

## 6. Alumni Core標準機能

Alumni Coreでは、一般的な自由入力ページに加えて、同窓会サイトに特有の機能を標準提供する。

- 人物挨拶
- 規約類
- 同窓会組織図
- 校歌・校訓
- 役員・理事一覧
- 卒業期早見表
- お知らせ
- イベント
- 卒業生の声（将来プラグイン等から参加可能）
- 汎用フォームエンジン

### 6.1 規約類

規約類はAlumni Core固有機能として扱う。

通常のWordPress Block Editorで本文を入力できることを必須とする。

本文では、少なくとも以下の標準ブロック編集を利用できる。

- 段落
- 見出し
- 太字
- 文字サイズ
- リスト

規約ごとに規約名、本文、更新・改訂履歴、改訂日等を管理できる。

本文だけでも公開可能とし、不要なメディアを必須にしない。

### 6.2 同窓会組織図

同窓会組織図はAlumni Core固有機能とする。

組織図は画像ではなく、親子関係と表示順を持つツリー構造として管理する。

標準的な初期構造例：

```text
会長
├─ 副会長
│  ├─ 総務委員会
│  ├─ 事業委員会
│  └─ 広報委員会
└─ 事務局
   └─ 事務局長
```

各ノードは最低限以下を持つ。

- node_id
- parent_id
- name
- sort_order

任意の階層数に対応できる構造とする。

組織図の親子関係とMenu Structureの親子関係は完全に分離する。

将来的に役員・理事データと組織図ノードを関連付けられる拡張性は残すが、初期実装で人物データとの自動連携は必須としない。

### 6.3 校歌・校訓

「校歌・校訓」はAlumni Core固有の一つの機能として扱う。

校歌と校訓を別々のトップレベル機能にせず、一つの管理画面・公開ページにまとめる。

#### 校歌

管理項目：

- 校歌タイトル
- 作詞
- 作曲
- 歌詞
- 楽譜
- 音源

これらはすべて任意とする。

以下のような状態をすべて正常として扱う。

- 歌詞だけ
- 歌詞＋楽譜
- 歌詞＋音源
- 歌詞＋楽譜＋音源

楽譜はPDFまたは画像ファイルを添付できる。

複数ページの楽譜PDFにも対応する。

音源はMP3等のWordPressで利用可能な音声ファイルを登録できるようにし、公開側では標準的な音声プレーヤーで再生できるようにする。

音源が登録されていない場合はプレーヤーを表示しない。

#### 校訓

管理項目：

- 校訓
- 説明・由来等のテキスト
- 校訓画像

校訓画像は任意とし、テキストだけでも正常に公開できるようにする。

画像がない場合は空の画像領域や壊れた画像を表示しない。

### 6.4 人物挨拶（複数人物をまとめるグループページ方式）

人物挨拶は、個々の人物ごとに独立した公開ページを増やす方式ではなく、**挨拶テーマごとに1つの公開ページを持ち、その中に複数の人物を表示するグループページ方式**を正式仕様とする。

標準プリセットとして、以下の2つの人物挨拶グループを用意する。

1. 母校校長挨拶
2. 同窓会長挨拶

公開メニューおよび標準表示順も、**母校校長挨拶 → 同窓会長挨拶**を基本とする。

#### グループと人物の関係

例：

```text
母校校長挨拶（1ページ）
├─ 現校長
├─ 前校長
└─ 歴代校長

同窓会長挨拶（1ページ）
├─ 現会長
├─ 前会長
└─ 歴代会長
```

個々の人物データは、それぞれ氏名・肩書・本文等を持つが、公開URL・メニューは原則としてグループ単位で提供する。

したがって、新しい校長や会長が就任した場合でも、新しい独立ページやメニューを作成する必要はない。既存グループへ人物を追加し、旧任者を歴代として保持する。

#### 管理画面での人物登録項目

各人物挨拶は最低限以下を管理できるようにする。

- 氏名
- 肩書
- 挨拶本文
- プロフィール写真または人物画像（任意）
- 所属する人物挨拶グループ
  - 母校校長挨拶
  - 同窓会長挨拶
- 就任開始日または開始年度（任意）
- 退任日または終了年度（任意）
- 現任者フラグ
- 手動表示順

将来、必要に応じて略歴等の追加項目を拡張できる構造とする。

#### 保存データの考え方

人物挨拶グループと個々の人物データを分離して管理する。

```text
Person Greeting Group
  group_id
  title
  slug
  sort_order

Person Greeting
  person_id
  group_id
  name
  title
  content
  image
  term_start
  term_end
  is_current
  sort_order
```

公開ページはグループを正本とし、人物は必ず1つのグループに所属する。

#### 公開時の表示順

原則として以下の順序とする。

1. **現任者を先頭**
2. 歴代人物は任期の新しい順
3. 同条件の場合は管理画面の手動表示順

これにより、通常は「現任者 → 直前の歴代 → 古い歴代」の順に表示される。

管理者は例外的な掲載順が必要な場合に、手動表示順で調整できるようにする。

#### グループページの公開仕様

「母校校長挨拶」「同窓会長挨拶」は、それぞれ1つの公開ページとして表示する。

各ページでは所属人物を同一ページ内に複数表示する。

人物が未登録の場合でも、グループ入口自体は標準プリセットとして保持できる。ただし公開側で空の人物カード等を表示しない。

架空の人物名や本文は初期データとして登録しない。管理者が実際の人物情報を追加する。

> 正式原則：人物挨拶は「1人物 = 1公開ページ」ではなく、「1挨拶テーマ = 1公開ページ、その中に複数人物を表示する」方式とする。


### 6.5 汎用フォームエンジン v1

Alumni Coreには、問い合わせ、参加申込、アンケート、各種エントリー等に共通利用できる**汎用フォームエンジン**を標準機能として追加する。

管理者がフォーム項目を定義し、公開URLを発行する。公開フォームから送信された内容は、フォームごとに指定したメールアドレスへ送信する。

#### 目的と基本原則

- フォームごとに入力項目を管理画面から定義できる
- フォームごとに公開URLを持つ
- Submit時にサーバー側で必須・形式等を検証する
- 正常な送信内容を指定メールアドレスへ送信する
- Themeに依存せず、Alumni Coreを正本としてフォーム定義・検証・送信を管理する
- Themeは公開フォームの見た目を担当し、フォームの項目定義や送信先を独自管理しない
- V1では一般的な公開フォームを対象とし、会員ログインを前提にしない

#### 管理画面構成

Alumni Core管理メニューに「フォーム」を独立した管理入口として追加する。

管理者は以下の流れでフォームを作成する。

```text
フォーム一覧
  ↓
新規フォームを追加
  ↓
基本設定
  ↓
入力項目を追加・編集・並び替え
  ↓
送信先メールアドレスを設定
  ↓
公開
```

フォーム編集画面は少なくとも以下の領域で構成する。

**1. 基本情報**

- フォーム名
- 公開スラッグ
- 説明文（任意）
- 公開状態

**2. 入力項目**

各項目について以下を設定できる。

- 項目ラベル
- 項目キー
- 項目種別
- 必須 / 任意
- 補足説明・プレースホルダー（任意）
- 選択肢（選択系項目）
- 表示順

V1の標準項目種別は以下とする。

- 1行テキスト
- メールアドレス
- 電話番号
- 数値
- 複数行テキスト
- セレクトボックス
- ラジオボタン
- チェックボックス

項目は管理画面上で追加・削除・編集・表示順変更できる。

**3. 送信設定**

- 送信先メールアドレス（必須）
- メール件名
- 送信完了メッセージ
- 送信者への自動返信の有効 / 無効

V1では送信先メールアドレスはフォームごとに設定する。

#### データモデル

フォーム本体はAlumni Core管理下の独立したフォームエンティティとして扱う。

論理モデルは以下とする。

```text
Form
  form_id
  title
  slug
  description
  status
  recipient_email
  mail_subject
  success_message
  auto_reply_enabled
  created_at
  updated_at

Form Field
  field_id
  form_id
  field_key
  label
  field_type
  required
  help_text
  placeholder
  options
  sort_order
```

実装上はWordPress標準の投稿・メタデータ機構を利用してよいが、テーマ固有データとして保存してはならない。

- フォーム定義はAlumni Coreが管理する
- 項目定義はフォームに従属する
- field_keyは同一フォーム内で一意とする
- 表示順は `sort_order ASC` を正本とする
- 同順位の場合は安定した一意ID昇順を使用する

V1では、フォーム定義と送信処理を必須範囲とする。送信履歴を管理画面で長期保管・検索する高度なワークフローはV1の必須要件としない。

#### 権限

フォーム定義の作成・編集・削除・公開および送信先メールアドレスの変更は、Alumni Coreの管理権限を持つユーザーに限定する。

最低限、以下を満たす。

- 権限のない公開ユーザーはフォーム定義を変更できない
- 公開ユーザーは公開済みフォームへの入力・送信のみ行える
- 非公開フォームの公開URLは送信を受け付けない
- 送信先メールアドレスをHTMLやJavaScript上へ露出させない

独自Capabilityを導入する場合も、Alumni Core内で一貫して管理する。

#### バリデーション

バリデーションはクライアント側だけに依存してはならない。

ブラウザ上の入力補助に加え、送信時に必ずサーバー側で再検証する。

最低限のV1ルールは以下とする。

- 必須項目は空送信不可
- メールアドレス型はWordPress/PHP標準の妥当なメール形式チェック
- 数値型は数値として検証
- 選択系項目は定義済み選択肢のみ受理
- field_keyを直接改ざんして未定義項目を送っても、メール本文へ無制限に混入させない
- 不正または不足がある場合は送信せず、項目単位でエラーを表示する

すべての送信値は、項目種別に応じてサニタイズ・エスケープする。

#### メール送信

正常な送信が完了した場合、フォームに設定された送信先メールアドレスへメールを送信する。

メール本文には、少なくとも以下を含める。

- フォーム名
- 送信日時
- 入力項目ラベル
- 入力値

メール送信はWordPress標準のメール送信機構を利用することを基本とする。

送信先メールアドレスはサーバー側設定として保持し、公開画面へ表示しない。

メール送信に失敗した場合は、利用者に「送信完了」と誤認させてはならない。成功・失敗を区別し、失敗時は再送可能な状態を維持する。

自動返信を有効にする場合は、フォーム内のメールアドレス項目を返信先として利用し、メールアドレス項目が存在しないフォームでは自動返信を送らない。

#### セキュリティと送信保護

公開フォームには最低限以下の対策を適用する。

- WordPress nonce等によるCSRF対策
- サーバー側バリデーション
- 出力時エスケープ
- 送信先メールアドレスの非公開
- 自動送信対策としてのハニーポット等、通常利用者に負担をかけない仕組み

V1ではCAPTCHAを必須としない。

#### 公開URL

各フォームは公開スラッグを持ち、個別の公開URLでアクセスできるようにする。

標準URL体系は以下とする。

```text
/forms/{slug}/
```

例：

```text
/forms/entry/
```

URLはフォームのタイトルではなく、明示的に管理されるslugを正本とする。

Menu StructureからフォームURLを参照できる構造を維持するが、フォームを作成しただけで自動的にグローバルメニューへ追加してはならない。

フォームの公開URLは通常の自由コンテンツURLとは別のフォーム専用ルーティングとして扱う。

#### 公開画面

公開ページでは、フォーム名、説明文、定義された入力項目、送信ボタンを表示する。

表示順は `sort_order ASC`、同順位時は一意ID昇順とする。

必須項目には必須であることを明確に表示する。

送信成功時はフォーム設定の完了メッセージを表示する。

PC・スマートフォンともに利用可能なレスポンシブ表示を必須とする。

ThemeはAlumni Coreが提供するフォーム定義を受け取り、サイトのデザインに合わせて表示してよいが、必須判定・項目定義・送信先・サーバー側検証の責務を持たない。

#### 受け入れ条件

以下を満たした場合、汎用フォームエンジン v1は受け入れ可能とする。

1. 管理者が新しいフォームを作成できる
2. 管理者が複数の入力項目を追加・編集・削除・並び替えできる
3. 必須 / 任意を項目ごとに設定できる
4. テキスト、メール、電話、数値、複数行、セレクト、ラジオ、チェックボックスを利用できる
5. フォームごとに送信先メールアドレスを設定できる
6. 公開済みフォームが `/forms/{slug}/` で表示される
7. 正常送信時、入力内容が指定メールアドレスへ送信される
8. 必須不足や形式不正時はメール送信されず、利用者へエラーが表示される
9. メール送信失敗時に成功メッセージを表示しない
10. 非公開フォームは公開URLから送信できない
11. 送信先メールアドレスが公開HTMLに表示されない
12. CSRF対策とサーバー側バリデーションが実装されている
13. PC・スマートフォンで入力・送信できる
14. フォームを作成しただけでMenu Structureへ自動追加されない
15. 既存の自由コンテンツ、人物挨拶、規約類、ニュース・イベントのURLや表示を破壊しない

> 正式原則：フォームの「項目定義・検証・送信」はAlumni Coreが管理し、「見せ方」はThemeが担当する。


## 7. 標準Menu Structureプリセット

新規インストール時の標準構造は以下を基本とする。

```text
ホーム

共通
├─ 母校校長挨拶
├─ 同窓会長挨拶
├─ お知らせ
├─ イベント
└─ 校歌・校訓

卒業生向け
└─ 同窓会情報
   ├─ 同窓会組織図
   ├─ 役員・理事紹介
   ├─ 規約類
   └─ 卒業期早見表

在校生向け
└─ 卒業生の声
```

これは新規サイトの初期プリセットであり、導入先ごとに管理者が自由に変更できる。

### 7.1 プリセット生成ルール

初期プリセットは新規サイトの初期セットアップ用である。

既存サイトを破壊してはいけない。

- 既存Menu Structureをリセットしない
- 既存Menu Structureを上書きしない
- 管理者が変更したメニューを勝手に戻さない
- 既存コンテンツを削除しない
- 既存URLを変更しない
- プラグイン更新のたびに再生成しない
- 再実行しても重複させない

架空の学校名、人物名、規約本文、校歌、音源等を本番公開用データとして自動投入しない。

「同窓会長挨拶」「母校校長挨拶」等は入口だけを用意する。

## 8. トップページ / Homepage Grid

トップページは、固定された機能配置ではなく、管理者が表示内容を自由に選択できるグリッドとして管理する。

### 8.1 基本レイアウト

V1の基本レイアウトは**横3列 × 縦2段**とする。

```text
┌─────────┬─────────┬─────────┐
│    A    │    B    │    C    │
├─────────┼─────────┼─────────┤
│    D    │    E    │    F    │
└─────────┴─────────┴─────────┘
```

6セルを基本単位とする。

### 8.2 各セルの自由選択

A〜Fの各セルについて、管理者が何を表示するかを選択できるようにする。

候補はAlumni Coreの標準機能・公開コンテンツを基礎とする。

例：

```text
A：母校校長挨拶
B：同窓会長挨拶
C：校歌・校訓
D：お知らせ
E：今後のイベント
F：卒業生の声
```

別のサイトでは、例えば組織図、役員・理事、規約類、自由コンテンツ等を配置してもよい。

トップページの配置とMenu Structure上の所属は独立している。

### 8.3 縦方向セル結合

必要に応じて、上下2段のセルを1つの表示領域として結合できるようにする。

例えばA+Dを結合した場合：

```text
┌─────────┬─────────┬─────────┐
│         │    B    │         │
│         ├─────────┤         │
│    A    │    E    │    C    │
│         │         │         │
└─────────┴─────────┴─────────┘
```

内部的にはrow / column / rowspan等で表現できる構造とし、将来のレイアウト拡張を妨げない。

管理画面ではCSS Gridの内部実装を意識させず、セル選択と結合操作を直感的に行えるUIとする。

V1では**上下方向の結合のみ**を対象とし、左右方向の結合や完全自由配置は将来拡張とする。

### 8.4 初期Homepage配置

新規サイトの初期値としては以下を推奨する。

```text
A：母校校長挨拶
B：同窓会長挨拶
C：校歌・校訓
D：お知らせ
E：今後のイベント
F：卒業生の声
```

これは初期値であり、管理者は自由に差し替えられる。

### 8.5 レスポンシブ表示

PCでは3列×2段を基本とする。

スマートフォン等の狭い画面では、セルを1列に積み上げて表示する。

縦結合セルは1つの表示ブロックとして扱う。

固定pxによる配置ではなく、CSS Grid等のレスポンシブなレイアウトで実現する。

## 9. トップページとMenu Structureの関係

サイト階層とトップページ上の配置は別概念として管理する。

例えば、

```text
Menu Structure
卒業生向け ＞ 同窓会情報 ＞ 同窓会組織図
```

であっても、トップページでは任意のセルに組織図を表示できる。

逆に、トップページに表示したからといってMenu Structureの所属を変更してはいけない。

## 10. お知らせ・イベントのトップページ表示

トップページでは、お知らせ・イベントを大きなカードとして表示せず、コンパクトな1行リストを基本とする。

### お知らせ

```text
[日付] [タイトル]
```

更新日はトップページでは省略する。

### イベント

イベントは以下の2つに分ける。

```text
今後のイベント
終了したイベント
```

今後のイベント：

- 今日を含む
- 今日・未来の日付
- 日付昇順
- 近いイベントを先頭
- 最大3件

終了したイベント：

- 昨日以前
- 日付降順
- 最近終了したイベントを先頭
- 最大3件

基準日はWordPressサイトのタイムゾーンに従う。

## 11. ナビゲーション表示

グローバルナビゲーションは基本的に以下とする。

```text
ホーム | 共通 | 卒業生向け | 在校生向け
```

お知らせ、イベント、卒業期早見表、役員・理事、規約類、組織図等をThemeが勝手に最上位へ追加してはいけない。

### Simple

上部ナビゲーションを使用する。

- hoverで即座にサブメニューを開く
- focus-withinでも開く
- 親 → 子 → 孫を右方向へカスケード表示
- 親からサブメニューへマウス移動しても消えない
- メニュー領域から離れると閉じる
- タッチ端末ではクリックをfallbackとして使用

### Formal

左サイドナビゲーションを使用する。

- hoverでは開かない
- クリックで開閉
- 各フォルダを独立してaccordion展開できる

両Themeとも同じMenu Structureデータを利用する。

## 12. 管理画面の原則

管理者がHTMLやURLを直接編集しなくても、機能別の入口から情報を作成し、Menu Structureで公開位置を決められることを目指す。

```text
何を作るかを選ぶ
↓
専用機能 / コンテンツを登録
↓
Menu Structureで配置
↓
必要ならHomepage Gridでトップページへ配置
```

フォルダはMenu Structure側で作成する。

コンテンツ編集画面に「フォルダ」というコンテンツ種別を設けない。

## 13. 標準サイト構成の考え方

新規サイトでは、Alumni Coreを有効化した時点で、同窓会サイトとして最低限成立する骨格を提供する。

```text
ホーム

共通
├─ 母校校長挨拶
├─ 同窓会長挨拶
├─ お知らせ
├─ イベント
└─ 校歌・校訓

卒業生向け
└─ 同窓会情報
   ├─ 同窓会組織図
   ├─ 役員・理事紹介
   ├─ 規約類
   └─ 卒業期早見表

在校生向け
└─ 卒業生の声
```

これは「完成済みの学校サイト」を自動生成するものではない。

学校固有の人物、規約、校歌、校訓、組織等は管理者が入力する。

## 14. 将来拡張

この情報設計を維持することで、将来以下のコンテンツを追加しても同じMenu StructureとHomepage Gridへ参加できる。

- Alumni-Voices
- Teacher's Voice
- 同窓会活動報告
- 会報
- キャリア情報
- 同期会・OB/OG会情報
- 沿革
- その他の同窓会発信コンテンツ

Homepage Gridについても、V1では3×2を基本とするが、将来的に3×3、2×2、全幅、2:1等のレイアウトを追加できる設計余地を残す。

## 15. 最終原則

> 「何を表示するか」と「どこに属するか」と「どう見せるか」を分離する。

Alumni Coreが情報・専用機能・Menu Structure・Homepage配置情報を管理し、Themeがそれを適切なUIへ変換する。
