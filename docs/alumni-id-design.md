# Alumni ID 設計

## 1. 目的

Alumni Core で管理する卒業生には、WordPress の自動採番IDとは別に、卒業年から人間が概ね判別できる **Alumni ID（会員番号／名簿番号）** を付与する。

例：

```text
1996年卒
├── 1996001
├── 1996002
├── 1996003
└── ...
```

このIDは Alumni Voices、Alumni Directory、Alumni Mail など、同窓会プラットフォーム全体で共通利用する。

---

# 2. ID形式

基本形式は以下とする。

```text
YYYYSSS
```

- `YYYY`：卒業年（西暦4桁）
- `SSS`：その卒業年内での連番（3桁、001〜999）

例：

| 卒業年 | 連番 | Alumni ID |
|---|---:|---:|
| 1996 | 001 | 1996001 |
| 1996 | 002 | 1996002 |
| 1996 | 123 | 1996123 |
| 2026 | 001 | 2026001 |

表示・検索・CSV連携では文字列または数値のどちらでも扱えるが、DB上は **BIGINT UNSIGNED** とする。

---

# 3. DB上のID方針

`wp_alumni` には2種類のIDを持たせる。

| カラム | 用途 |
|---|---|
| `id` | 内部用サロゲートキー（BIGINT AUTO_INCREMENT） |
| `alumni_id` | 卒業年＋連番で構成する外部表示用ID |

例：

```text
id         = 357
alumni_id  = 1996001
graduation_year = 1996
```

## なぜ `id` を廃止しないか

`1996001` を主キーそのものにすることも可能だが、内部処理では AUTO_INCREMENT のサロゲートキーを維持する。

理由：

- 卒業年不明の卒業生が存在する可能性がある
- 後から卒業年が訂正される可能性がある
- 連番の採番ルール変更に内部の外部キーを巻き込まない
- 他テーブルの外部参照を安定させる

したがって、**内部参照は `id`、人間向け・外部連携は `alumni_id`** とする。

---

# 4. `wp_alumni` の追加定義

```text
id                BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
alumni_id         BIGINT UNSIGNED NULL UNIQUE
graduation_year   SMALLINT UNSIGNED NULL
```

主なインデックス：

```text
PRIMARY KEY (id)
UNIQUE KEY alumni_id (alumni_id)
INDEX graduation_year
```

`alumni_id` は卒業年が確定している場合に採番する。

---

# 5. 採番ルール

## 5.1 新規登録時

卒業年が入力済みの場合、Alumni Core が同じ卒業年の最大連番を確認し、次の番号を採番する。

概念：

```text
1996年卒の既存最大ID
1996037

↓

次の登録
1996038
```

## 5.2 削除・アーカイブ後

一度採番した Alumni ID は再利用しない。

例：

```text
1996001
1996002 ← アーカイブ
1996003
```

次の新規登録は `1996004` とする。

欠番があっても詰めない。

## 5.3 卒業年不明

卒業年が不明な場合は、無理に `YYYYSSS` を採番しない。

```text
alumni_id = NULL
graduation_year = NULL
```

として保存し、卒業年が確定した時点で採番する。

管理画面では「ID未採番」と表示する。

---

# 6. 卒業年の訂正

卒業年が後から変更される場合があるため、以下のルールとする。

## 原則

一度発行した `alumni_id` は通常変更しない。

理由は、CSV、メール配信履歴、外部資料などで参照される可能性があるため。

例：

```text
登録時：1996年卒 → alumni_id 1996001

後日訂正：1995年卒
```

この場合、原則として `alumni_id` は `1996001` のまま保持し、卒業年だけ `1995` に訂正する。

## 例外：採番前または管理者による再採番

初期移行や誤登録の修正段階では、権限を持つ管理者が再採番できるようにする。

ただし再採番は通常編集とは分け、確認画面を必須とする。

---

# 7. 1000人を超える場合

通常の高校の同一卒業年で999人を超えることは想定しにくいが、拡張性を考慮する。

基本表示は3桁連番：

```text
1996001
```

999人を超える場合は4桁以上を許可する。

```text
1996999
19961000
```

ただし、実装では文字数固定ではなく「卒業年＋連番」の連結として生成する。

---

# 8. 同時登録時の採番競合対策

単純に「MAX + 1」をアプリケーション側だけで処理すると、同時登録で同じ番号が発生する可能性がある。

Alumni Core では以下を満たす実装とする。

1. `alumni_id` に UNIQUE INDEX を設定
2. 採番とINSERTをできるだけ同一トランザクションで処理
3. UNIQUE競合時は最大値を再取得してリトライ

必要に応じて、卒業年ごとの採番管理テーブルを将来導入できる。

例：

```text
wp_alumni_id_sequences

id
graduation_year UNIQUE
last_sequence
updated_at
```

ただしMVPでは、実際の運用規模を考慮し、`MAX + 1` + UNIQUE制約 + リトライで開始してよい。

---

# 9. 管理画面での扱い

Alumni Directory の卒業生一覧では、先頭列または氏名の近くに Alumni ID を表示する。

例：

```text
Alumni ID | 氏名       | 卒業年 | 期
1996001   | 山田 太郎  | 1996   | 25
1996002   | 佐藤 花子  | 1996   | 25
```

新規登録画面では、原則として管理者がIDを入力しない。

```text
卒業年：1996

Alumni ID：自動採番予定（1996xxx）
```

保存時に確定する。

---

# 10. 検索・CSV・外部連携

Alumni ID は以下で利用する。

- WordPress管理画面での直接検索
- CSVインポート時の既存人物照合
- CSVエクスポート
- Alumni Voicesとの人物紐付け
- Alumni Mailの配信対象確認
- 将来の会員向け問い合わせ番号

ただし、メールアドレスや氏名と異なり、Alumni IDだけでは本人確認を行わない。

---

# 11. 既存DB設計との関係

この設計は既存の Alumni Core DB 設計を補完する。

他の関連テーブルは引き続き内部キー `wp_alumni.id` を `alumni_id` として参照する。

```text
wp_alumni
├── id = 内部キー
└── alumni_id = 卒業年＋連番

wp_alumni_emails.alumni_id
    └── wp_alumni.id を参照
```

ここで `alumni_id` という名称が「外部表示ID」と「他テーブルの外部キー」で混同しやすいため、実装時には以下の命名を推奨する。

```text
wp_alumni
id
member_number
```

または

```text
id
public_id
```

### 推奨最終命名

```text
id          = 内部キー
member_id   = 1996001形式の同窓会共通ID
```

この文書では説明上「Alumni ID」と呼ぶが、実DBカラム名は `member_id` を推奨する。

---

# 12. 最終設計

```text
内部ID（id）
    ↓
DB間の安定した参照

同窓会ID（member_id）
    ↓
卒業年＋連番
例：1996001
    ↓
人間が確認・検索・CSV・外部連携に使用
```

この二層構造により、内部データの安定性と、人間に分かりやすい同窓会固有IDの両立を実現する。
